Most frameworks:   you define tools    →  model picks one     →  the tool runs
JarvisCore:        you describe a goal →  model writes Python →  a sandbox runs it

And when you'd rather not leave something to a model, you write that part yourself. That choice is the whole API surface.

Two profiles. One mesh.

ProfileYou writeThe framework writesReach for it when
CustomAgentexecute_task(): the logicMesh routing, discovery, lifecycle, infrastructure injectionThe answer is deterministic. Don't pay a model to do arithmetic.
AutoAgentrole, capabilities, system_promptLook-decide-act loop, planning, tool generation, sandboxed execution, self-repairThe work needs judgement: reviewing, writing, deciding.

Our squad uses both. That's not a demo contrivance, it's the actual rule: deterministic work goes in code, judgement goes in a prompt.

JarvisCore basics09 / 18

An AutoAgent is three attributes.

class Inspector(AutoAgent):
    role          = "inspector"
    capabilities  = ["code_analysis", "security_analysis"]
    system_prompt = """You review code that is already on GitHub..."""

No tool definitions. No JSON schema. No executor wiring. The kernel plans the steps, writes the Python, runs it in a sandbox, and repairs it when it fails.

What those three do
  • roleThe name other agents route to.
  • capsWhat it advertises to the mesh, so work finds it.
  • promptThe job description. This is where your thinking goes.

class WarehouseAgent(CustomAgent):

    async def execute_task(self, task):
        # you write this. no model involved, no tokens spent.
        return {"status": "success", "output": {...}}

Same mesh, same routing, same infrastructure injection: you just supply the body. Use it wherever a model would only add latency and risk.

JarvisCore basics11 / 18

The mesh is four lines.

mesh = Mesh(config={"nexus_gateway_url": ..., "redis_url": ...})
mesh.add(CodeSmith)
mesh.add(Inspector)
mesh.add(Reporter)
await mesh.start()

results = await mesh.workflow("review", [
    {"agent": "codesmith", "task": "Write it and push it"},
    {"agent": "inspector", "task": "Review it", "depends_on": [0]},
    {"agent": "reporter",  "task": "Email it",  "depends_on": [1]},
])

depends_on is the whole orchestration language. Steps with no dependency between them run in parallel; the engine handles claiming, retries and crash recovery.

Judgement in a prompt. Mechanics in code.

The three agents decide things
  • 1CodeSmith: what does plausible-but-flawed payments code look like?
  • 2Inspector: which of these are real defects, and how bad?
  • 3Reporter: what does someone actually need to read?
Six calls stay ordinary Python 
create_branch()
commit_file()
read_file()
open_pr()
comment_on_pr()
send_email()

Deterministic, so a model adds nothing but risk, and printing every one of them is what makes the run followable.

Same credential guarantee either way: every call goes through proxy.call(connection_id, …). Ask which half a job belongs in before you write it. That one question is most of the design.

What you need, and what you don't.

Need
  • ✓Python 3.10+
  • ✓pip install jarviscore-framework[redis]
  • ✓Docker, for Redis: one compose command
  • ✓One LLM credential, from whoever you like. JarvisCore is model-agnostic: Azure OpenAI, Anthropic, Gemini, or any OpenAI-compatible endpoint
  • ✓A GitHub account
Don't need
  • –A second model provider: one credential covers the whole demo
  • –A Google Cloud project: the gateway already has a client on google-workspace
  • –Any vector database
  • –A Nexus deployment: we used ours on the day
  • –To have written an agent before

The build15 / 18

Your agent never holds the token.

What the agent writes 
async def main():
    r = await nexus_call("PUT", url,
            json={"content": b64})
    return {"success": r["ok"]}

One door. No headers, no secrets, nothing to leak.

What Nexus does

Resolves an opaque connection_id to a live credential, applies it to the request, and returns only the response.

Nexus is also where the provider gets registered in the first place: catalog, OAuth consent, token refresh, revocation.

Proof, live: after a run we grep the generated code for token|secret|bearer and get nothing back.
